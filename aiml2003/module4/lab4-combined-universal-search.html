# Cell 3a–3c: Load and chunk your document

What it does: Opens a PDF or plain text file you upload to Colab, extracts all text, and chunks it into passages of roughly 300 words each. Three chunking strategies are available: fixed-size, overlapping, and sentence-boundary. Part 1 uses fixed-size by default; Experiment 5 revisits the others.

Your input: Upload a PDF or .txt file to Colab (Files panel → Upload). Set DOC_PATH at the top of Cell 3a to your filename. Aim for at least 10 pages of selectable text (not scanned images). You can find great texts for chunking and embedding at Project Gutenberg.

Caching: The cell copies your file to Google Drive (/content/drive/MyDrive/AIML_Lab_Cache) so you don’t have to re-upload in future sessions. If you want a different document later, delete the cached copy from Drive first.

Cell 3c lets you inspect chunk boundaries — where one chunk ends and the next begins. With fixed-size chunking, cuts happen mid-sentence. You’ll revisit this in Experiment 5.

# Cell 4: Load and preprocess images

What it does: Loads your image dataset, resizes all images to 224×224 for MobileNetV2, and applies the model’s preprocessing function. Also generates an index sheet (image_index_sheet.jpg) you’ll reference in Experiment 2.

Dataset choice: Set DATASET at the top of the cell. Two options:

  • flowers — Oxford/TF Flowers. Five species (daisy, dandelion, roses, sunflowers, tulips). Natural photos at 300–500px. Fine-grained: the classes look similar, so retrieval has to work harder.
  • imagenette — A 10-class subset of ImageNet (tench, English springer, cassette player, chain saw, church, French horn, garbage truck, gas pump, golf ball, parachute). Visually diverse: good for testing whether the model separates distinct objects.

Caching: Images and preprocessed arrays are cached to Google Drive. Subsequent runs load from cache.

# Cell 5: Embed text chunks

What it does: Loads the nomic-ai/nomic-embed-text-v1.5 sentence transformer and encodes all text chunks into 768-dimensional dense vectors.

Nomic Embed uses task-specific prefixes: "search_document: " when encoding passages for storage, "search_query: " when encoding a query at retrieval time. The prefix signals whether the input is a document or a question, which improves retrieval accuracy. It also supports Matryoshka embeddings — the first 256 or even 64 dimensions carry a disproportionate share of the information — but this lab uses the full 768.

Caching: Embeddings are cached to Google Drive.

# Cell 6: Extract image embeddings

What it does: Loads MobileNetV2 as a feature extractor (no classification head, global average pooling) and produces a 1,280-dimensional embedding per image.

Caching: Image embeddings are cached to Google Drive.

# Cell 7: Build ChromaDB collections

What it does: Creates an in-memory ChromaDB client with two independent collections: one for text chunks (768-dimensional) and one for image embeddings (1,280-dimensional). Populates both collections.

The cell includes a brief explanation of what a vector database is and why you need one. If you’re fuzzy on the difference between a traditional SQL query and a similarity search, read the markdown cell above this code carefully.

Cell 7b lets you peek inside the database — what a single record looks like in each collection, how the embedding vector is stored alongside the document text or image label.

# Cell 8: Search functions and RAG pipeline

What it does: Defines search_text(query, n) for text retrieval, search_images_by_image(query_idx, n) for image retrieval, and ask_document(question) for the full RAG pipeline (retrieve context, pass to Gemini, return answer). Tests all three with example queries.

The RAG system prompt instructs Gemini to use only the provided context. If the answer isn’t in the context, it should say so rather than guessing.

# Cell 9: Visualization helpers

What it does: Defines utility functions for displaying image retrieval results: query image on the left, nearest neighbors to the right, with labels, similarity scores, and correct/incorrect match markers.

Part 2: Experiments

Five experiments, each asking a different question about how these vector spaces work. Run the code, record what you find, and write the markdown reflection for each one. The reflections are the substance of your demo.

Experiment 1: The Similarity Game (Text)

The question: What makes a “good” query for a sentence embedding model? When you write a query by hand, what strategies produce the highest cosine similarity to a target passage?

The procedure:

  1. Run the cell to pick a random passage from your document and display it.
  2. Read the passage carefully.
  3. Write a query sentence — anything you think will score high similarity against that passage.
  4. The cell scores your query and logs it.
  5. Repeat at least five times. Try different strategies: exact vocabulary, synonyms, paraphrasing, short vs. long, abstract vs. concrete.

Experiment 2: The Similarity Game (Images)

The question: Does MobileNetV2’s ranking of “similar” match yours? When you look at an image and predict which others the model will rank as most similar, are you right?

The procedure:

  1. The cell displays your image index sheet — a grid of all images with their indices and class labels.
  2. Pick a query image. Before running retrieval, write down which image you predict will be the model’s #1 match and why.
  3. Run retrieval. Compare the model’s results to your prediction.
  4. Repeat for at least five images from different classes.

Experiment 3: Embedding Surgery

The question: Embedding vectors aren’t just opaque numbers — they have geometric structure. If you average two embeddings, does the midpoint land somewhere meaningful?

The procedure:

  1. Pick two text chunks on different topics. Average their embeddings. Retrieve the closest passage to the midpoint.
  2. Pick two images from different classes. Average their embeddings. Retrieve the closest image to the midpoint.
  3. Try it with three embeddings.
  4. Try averaging two embeddings from the same class or topic. Does the midpoint retrieve something “more typical” of that category?

Experiment 4: The Caption Bridge Autopsy

The question: You can’t query images with text because the embeddings live in different vector spaces (768d text vs. 1,280d image). But what if you translate an image into text first? Gemini Vision can caption an image, and that caption can be embedded as text and used to search the text collection. How much information survives this translation?

The procedure:

  1. Run the caption bridge on five images from different classes.
  2. For each image, examine three things: what the image actually shows, what Gemini’s caption says, and what the text retrieval finds using that caption.
  3. Rate each step of the chain: did the caption capture the image’s content? Did the text retrieval find something relevant to the caption?
  4. Connect this back to Experiment 1: is Gemini writing “good queries” by the standards you discovered?

Experiment 5: Chunking Strategy Showdown

The question: You used fixed-size chunking to build the vector database in Part 1. But chunking strategy affects everything downstream — the quality of your embeddings, the relevance of your retrievals, and the accuracy of your RAG answers. Does it actually matter which strategy you use? And for overlap chunking, how much overlap is the right amount?

The procedure:

  1. Write three questions your RAG pipeline can answer well (you tested these in Part 1).
  2. Run the strategy comparison to test fixed, overlap, and sentence-boundary chunking on those questions.
  3. Run the overlap sweep: try different overlap amounts (25, 50, 100, 150 words) and see how overlap size affects chunk count, retrieval distance, and which passage gets retrieved. Find the sweet spot for your document.
  4. Pick your best configuration and run a full RAG answer comparison against the default. Did the answer actually improve?
