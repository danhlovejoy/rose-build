One document. One vector database. What does “similar” actually mean?

This lab is different from previous labs.

# Cell 1: Setup and dependencies

What it does: Installs all libraries for the text pipeline and imports everything. Prints version numbers for key dependencies.

Installs: chromadb, sentence-transformers, pymupdf, google-genai, einops.

Note: The installs take 30–60 seconds. If chromadb throws a dependency conflict warning, it is safe to ignore. Wait for the “All imports succeeded” message before moving on.

# Cell 2: Configure the Gemini API

What it does: Loads your Gemini API key from Colab Secrets and creates a Gemini client. Sends a test prompt to confirm the connection.

Note: If you get an authentication error, check that the secret is named exactly GEMINI_API_KEY and that notebook access is toggled on.

# Cells 3a–3c: Load and chunk your document

What it does: Opens a PDF or plain text file you upload to Colab, extracts all text, and chunks it into passages of roughly 300 words each. Three chunking strategies are available: fixed-size, overlapping, and sentence-boundary. Part 1 uses fixed-size by default; Experiment 4 revisits the others.

Your input: Upload a PDF or .txt file to Colab (Files panel → Upload). Set DOC_PATH at the top of Cell 3a to your filename. Aim for at least 10 pages of selectable text (not scanned images). You can find great texts for chunking and embedding at Project Gutenberg.

Caching: The cell copies your file to Google Drive (/content/drive/MyDrive/AIML_Lab_Cache) so you don’t have to re-upload in future sessions. If you want a different document later, delete the cached copy from Drive first.

Cell 3c lets you inspect chunk boundaries — where one chunk ends and the next begins. With fixed-size chunking, cuts happen mid-sentence. You’ll revisit this in Experiment 4.

# Cell 4: Embed text chunks

What it does: Loads the nomic-ai/nomic-embed-text-v1.5 sentence transformer and encodes all text chunks into 768-dimensional dense vectors.

Nomic Embed uses task-specific prefixes: "search_document: " when encoding passages for storage, "search_query: " when encoding a query at retrieval time. The prefix signals whether the input is a document or a question, which improves retrieval accuracy.

Caching: Embeddings are cached to Google Drive.

# Cells 5–5b: Build ChromaDB text collection

What it does: Creates an in-memory ChromaDB client with a text collection containing all chunks and their embeddings. Cell 5b lets you peek inside the database — what a single record looks like, how the embedding vector is stored alongside the document text.

Traditional databases store rows and match exact keywords. Vector databases store embedding vectors and match by similarity — give me the 3 nearest vectors to this query. SQL matches words. Vectors match meaning.

# Cell 6: Search functions and RAG pipeline

What it does: Defines search_text(query, n) for text retrieval and ask_document(question) for the full RAG pipeline (retrieve context, pass to Gemini, return answer). Tests both with an example query.

The RAG system prompt instructs Gemini to use only the provided context. If the answer isn’t in the context, it should say so rather than guessing.

Part 2: Experiments

Four experiments, each asking a different question about how the text vector space works. Run the code, record what you find, and write the markdown reflection for each one. The reflections are the substance of your demo.

Experiment 1: The Similarity Game

The question: What makes a “good” query for a sentence embedding model? When you write a query by hand, what strategies produce the highest cosine similarity to a target passage?

The procedure:

  1. Run the cell to pick a random passage from your document and display it.
  2. Read the passage carefully.
  3. Write a query sentence — anything you think will score high similarity against that passage.
  4. The cell scores your query and logs it.
  5. Repeat at least five times. Try different strategies: exact vocabulary, synonyms, paraphrasing, short vs. long, abstract vs. concrete.

Experiment 2: Embedding Surgery

The question: Embedding vectors aren’t just opaque numbers — they have geometric structure. If you average two embeddings, does the midpoint land somewhere meaningful?

The procedure:

  1. Pick two text chunks on different topics. Average their embeddings. Retrieve the closest passage to the midpoint.
  2. Try it with three chunks on three different topics.
  3. Try averaging two chunks on the same topic. Does the midpoint retrieve something “more typical” — a more prototypical passage?
  4. Try subtracting: take chunk A’s embedding, subtract chunk B’s embedding, and retrieve the nearest passage. What does the “difference vector” point to?

Experiment 3: The Caption Bridge

The question: Your vector database indexes text. But what if you wanted to search it starting from an image? Gemini Vision can caption an image, and that caption can be embedded as text and used to search the text collection. How much information survives this translation?

The procedure:

  1. Run the setup cell to load a small set of sample images (flowers dataset, five classes).
  2. Run the caption bridge on five images from different classes.
  3. For each image, examine three things: what the image actually shows, what Gemini’s caption says, and what the text retrieval finds using that caption.
  4. Rate each step of the chain: did the caption capture the image’s content? Did the text retrieval find something relevant to the caption?
  5. Connect this back to Experiment 1: is Gemini writing “good queries” by the standards you discovered?

Experiment 4: Chunking Strategy Showdown

The question: You used fixed-size chunking to build the vector database in Part 1. But chunking strategy affects everything downstream — the quality of your embeddings, the relevance of your retrievals, and the accuracy of your RAG answers. Does it actually matter which strategy you use? And for overlap chunking, how much overlap is the right amount?

The procedure:

  1. Write three questions your RAG pipeline can answer well (you tested these in Part 1).
  2. Run the strategy comparison to test fixed, overlap, and sentence-boundary chunking on those questions.
  3. Run the overlap sweep: try different overlap amounts (25, 50, 100, 150 words) and see how overlap size affects chunk count, retrieval distance, and which passage gets retrieved. Find the sweet spot for your document.
  4. Pick your best configuration and run a full RAG answer comparison against the default. Did the answer actually improve?
