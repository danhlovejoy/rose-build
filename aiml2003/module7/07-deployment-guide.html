Deployment Guide: Notebook to Web App

AIML 2003: Introduction to Natural Language Processing

This guide walks you through converting a Colab notebook into a Hugging Face Spaces web app. Your audience interacts with a live app instead of watching you scroll through cells, and the deployment itself shows that you know the difference between training code and inference code.

The Mental Model: Two Halves of a Notebook

Every notebook you've written this semester has two kinds of code, even if you never thought about it that way:

  1. Setup and training code runs once and produces artifacts: loading a dataset, training a model, computing embeddings for a collection, building a TF-IDF matrix. This code is expensive (needs GPU, large datasets, long loops) and its output can be saved to a file.
  2. Inference code runs on every user request, using those artifacts: classifying one sentence, embedding one query, computing cosine similarity against a saved matrix. This code is cheap. One input, one output, sub-second on CPU.

The conversion separates these two halves. Your Colab notebook keeps the setup/training code and adds export cells at the end. Your app.py contains only the inference code, wrapped in a Gradio UI, loading artifacts from the files you exported.

Visually:

┌─────────────────────────────────────────────────┐
│  YOUR COLAB NOTEBOOK                            │

Step 1: Go Through Your Notebook Cell by Cell

Open your notebook and label each cell. Ask: "Does this cell need to run every time a user submits a query?" If no, it's setup code and stays in the notebook. If yes, it's inference code and goes into app.py.

Here's the Art Style Explorer notebook, cell by cell:

Cells 15 and 19 are the inference cells. Each takes one input (a text query or an image), encodes it with CLIP, and dot-products it against the pre-computed embedding matrix. Everything before Cell 15 built that matrix. Cells 21–22 package it for export.

Rule of thumb: If a cell touches your full dataset, it's setup. If it processes a single input, it's inference. The line between them is where you save artifacts.

Step 2: Add Export Cells to Your Notebook

After your training/computation code, add cells that save the artifacts your app will need. In the Art Style Explorer, that means saving the embedding matrix, the metadata, and the thumbnail images. This is Cell 21 in the notebook:

export_dir = "art_explorer_export"
os.makedirs(export_dir, exist_ok=True)
os.makedirs(f"{export_dir}/thumbnails", exist_ok=True)

# 1. Save embeddings — the (N, 512) matrix computed in Step 4
np.save(f"{export_dir}/image_embeddings.npy", image_embeddings)

# 2. Save metadata — one dict per artwork, same row order as the embeddings
metadata = []
for i, art in enumerate(artworks):
    metadata.append({
        "index": i,
        "title": art["title"],
        "artist": art["artist"],
        "date": art["date"],
        "medium": art["medium"],
    })

with open(f"{export_dir}/metadata.json", "w") as f:
    json.dump(metadata, f, indent=2)

# 3. Save thumbnails (resized for web, JPEG for small file size)
for i, art in enumerate(artworks):
    thumb = art["image"].copy()
    thumb.thumbnail((400, 400), Image.LANCZOS)
    thumb.save(f"{export_dir}/thumbnails/{i:03d}.jpg", quality=85)

The .npy file stores the embedding matrix. The .json file stores the metadata you want to display in search results (title, artist, date). The thumbnails are plain JPEGs that Gradio's Gallery component can render without any conversion.

Cell 22 zips everything for download:

with zipfile.ZipFile("art_explorer_export.zip", "w", zipfile.ZIP_DEFLATED) as zf:
    for root, dirs, files in os.walk(export_dir):
        for file in files:
            filepath = os.path.join(root, file)
            arcname = os.path.relpath(filepath, ".")
            zf.write(filepath, arcname)

print(f"Download art_explorer_export.zip from the Files panel")

Adapting this to your project

The same pattern (computation output + metadata + display assets) applies to other project types, with different formats. An sklearn classifier uses pickle.dump(model, f) to serialize the trained model and vectorizer; the app loads them with pickle.load(). Other embedding projects (sentence-transformers, ChromaDB) use the same .npy + .json approach. Gemini API projects might still have pre-computed data like chunked documents or few-shot examples worth exporting as JSON, but if the app is purely API-driven with no saved state, you can skip this step.

Download your exports before the Colab runtime disconnects. Click the folder icon in Colab's left sidebar, find your zip file, click the ⋮ menu, and choose Download. Colab deletes your files when the runtime recycles.
Always upload all exported files together. The embeddings, metadata, and thumbnails are row-aligned: row 0 in the embedding matrix corresponds to entry 0 in the metadata and thumbnail 000.jpg. If you re-run the notebook with a new collection and only upload some of the files to your Space, the rows go out of sync and search results will pair the wrong titles with the wrong images. Upload the zip's contents as a unit.

Step 3: Build app.py from Your Inference Code

Your app.py has three sections in order: imports and artifact loading (runs once at startup), inference functions (copied from your notebook), and the Gradio UI (new code that wraps your functions in a web interface). Each section maps directly from the Art Style Explorer notebook.

Section 1: Load artifacts

In the notebook, the data came from the Met API (Cells 8–9) and the embeddings were computed in a GPU loop (Cell 13). None of that runs in the app. The app loads the pre-computed results from disk:

import os, json
import numpy as np
import torch
import gradio as gr
from PIL import Image
from transformers import CLIPProcessor, CLIPModel

# ── Load the artifacts you exported from the notebook ──
EMBEDDINGS = np.load("image_embeddings.npy")
with open("metadata.json") as f:
    METADATA = json.load(f)
THUMB_DIR = "thumbnails"

# Load CLIP for single-query encoding (~600 MB)
device = "cuda" if torch.cuda.is_available() else "cpu"
model = CLIPModel.from_pretrained("openai/clip-vit-base-patch32")
processor = CLIPProcessor.from_pretrained("openai/clip-vit-base-patch32")
model = model.to(device)
model.eval()

This replaces Cells 3, 4, 6, 8, 9, and 13 from the notebook. All of the data collection and batch embedding is gone. What remains is loading CLIP itself (needed to encode queries at runtime) and loading the files you exported.

Section 2: Inference functions

These come directly from the notebook. Here's search_by_text side by side:

Notebook (Cell 15)

def search_by_text(query, top_k=5):
    inputs = processor(text=[query], return_tensors="pt", padding=True)
    inputs = {k: v.to(device) for k, v in inputs.items()}
    with torch.no_grad():
        text_out = model.text_model(**inputs)
        text_emb = model.text_projection(text_out.pooler_output)
    text_emb = text_emb / text_emb.norm(dim=-1, keepdim=True)
    scores = (text_emb.cpu().numpy() @ image_embeddings.T).flatten()
    top_idx = scores.argsort()[::-1][:top_k]
    return [(artworks[i], float(scores[i])) for i in top_idx]

app.py

def search_by_text(query):
    if not query or not query.strip():
        return []
    inputs = processor(text=[query.strip()], return_tensors="pt", padding=True)
    inputs = {k: v.to(device) for k, v in inputs.items()}
    with torch.no_grad():
        text_out = model.text_model(**inputs)
        text_emb = model.text_projection(text_out.pooler_output)
    text_emb = text_emb / text_emb.norm(dim=-1, keepdim=True)
    scores = (text_emb.cpu().numpy() @ EMBEDDINGS.T).flatten()
    top_idx = scores.argsort()[::-1][:8]

    results = []
    for i in top_idx:
        meta = METADATA[i]
        thumb = os.path.join(THUMB_DIR, f"{i:03d}.jpg")
        caption = f"{meta['title']}\n{meta['artist']}, {meta['date']}"
        results.append((thumb, caption))
    return results

Three things changed. The variable image_embeddings (computed by Cell 13 in the notebook) became EMBEDDINGS, loaded from the .npy file at startup. The return format switched from (artwork_dict, score) tuples (for matplotlib) to (filepath, caption) tuples (for Gradio's Gallery component). And the app validates input, checking for empty queries, because it accepts input from anyone.

The CLIP encoding logic is identical line for line: processor, model.text_model(), projection, normalization, dot product, device handling. You're changing the wrapper around the function, not the function.

The same four changes apply to search_by_image (Cell 19 → app.py). The CLIP encoding stays the same; the device handling and return format change.

Figuring out what UI your app needs

In a notebook, inputs are hardcoded. You typed query = "women in dresses" into a cell and ran it. You set query_idx = 0 to pick an artwork for image search. In a web app, a user provides those values, so each hardcoded input becomes a UI component.

Look at each inference function's arguments. Each argument the user should control maps to a Gradio input component:

Notebook code (hardcoded)What the user providesGradio component
query = "women in dresses"A text descriptiongr.Textbox
query_image = artworks[0]["image"]An uploaded imagegr.Image
top_k=5How many results to showgr.Slider (or keep it hardcoded)
results (list of artworks rendered by matplotlib)N/A (this is output)gr.Gallery expects (filepath, caption) tuples

The last row is an output, not an input. In the notebook, search_by_text returned a list of dictionaries that matplotlib rendered as a grid. In the app, that grid becomes a gr.Gallery, so the function returns (filepath, caption) tuples instead.

The same logic applies to any project. If your notebook has a cell where you type sentence = "This movie was terrible" and pass it to a classifier, that string becomes a gr.Textbox. If you load a test image from disk with Image.open("test.jpg"), that becomes gr.Image. If you have a dropdown-style choice (model A vs. model B, or a list of categories), that becomes gr.Dropdown. Every hardcoded value that a user should be able to change becomes a component.

Section 3: Gradio UI

The Gradio UI is the only section of app.py that doesn't come from the notebook. It defines what the user sees and wires components to your inference functions:

with gr.Blocks(title="Art Style Explorer") as demo:
    gr.Markdown("# Art Style Explorer")
    gr.Markdown("Search public-domain artworks using OpenAI CLIP.")

    with gr.Tab("Search by Text"):
        text_input = gr.Textbox(
            label="Describe what you're looking for",
            placeholder='Try: "stormy ocean at night"',
        )
        text_btn = gr.Button("Search", variant="primary")
        text_gallery = gr.Gallery(label="Results", columns=4, height="auto")
        text_btn.click(fn=search_by_text, inputs=text_input, outputs=text_gallery)
        text_input.submit(fn=search_by_text, inputs=text_input, outputs=text_gallery)

    with gr.Tab("Search by Image"):
        img_input = gr.Image(label="Upload an image", type="pil")
        img_btn = gr.Button("Find Similar", variant="primary")
        img_gallery = gr.Gallery(label="Similar Artworks", columns=4, height="auto")
        img_btn.click(fn=search_by_image, inputs=img_input, outputs=img_gallery)

demo.launch()

gr.Blocks gives you tabs, custom layout, and multiple inputs/outputs. The Art Style Explorer has two tabs (text search, image search), each wired to its own function. The .click() calls connect buttons to functions; .submit() lets the user press Enter in the text box.

Step 4: Choosing the Right Gradio Layout

Gradio has two API levels. The Art Style Explorer uses gr.Blocks because it has two modes (text search, image search). Simpler projects can use gr.Interface.

gr.Interface — one function, one set of inputs, one set of outputs

demo = gr.Interface(
    fn=your_function,           # the function Gradio calls
    inputs=gr.Textbox(...),     # what the user provides
    outputs=gr.Textbox(...),    # what they see back
    title="My App",
)
demo.launch()

Use this when your app does one thing: text in → text out, image in → label out. A sentiment classifier, a single-mode RAG query, or a captioning tool each have one function and fit naturally in gr.Interface.

gr.Blocks — tabs, multiple functions, custom layout

The Art Style Explorer uses gr.Blocks because it has two search modes that share the same embedding data but accept different input types. If your project has multiple modes, multiple steps, or needs a layout beyond "one input box → one output box," use gr.Blocks.

Connecting buttons to functions

In gr.Blocks, you wire components together with .click():

button.click(fn=your_function, inputs=[input1, input2], outputs=[output1])

When the user clicks the button, Gradio calls your_function(input1_value, input2_value) and puts the return value into output1. If your function returns a tuple, each element maps to the corresponding output component.

For text boxes, you can also use .submit() so pressing Enter triggers the function:

textbox.submit(fn=your_function, inputs=textbox, outputs=output)
Test locally first. Before uploading to Hugging Face, test your app.py on your own machine or in Colab. Run pip install gradio then python app.py. Gradio opens a local URL you can interact with. Fix bugs here, not in the deployment logs.

Step 5: Assemble Your HF Space Files

Your Space's repository contains everything the app needs to run. There's no cell-by-cell execution and no notebook state; app.py loads your exported files and starts a Gradio server.

The Art Style Explorer's file structure:

art-style-explorer/
├── app.py                  ← Gradio code (Section 1 + 2 + 3 from above)
├── requirements.txt        ← transformers, torch, Pillow, gradio, numpy
├── image_embeddings.npy    ← exported from notebook Cell 21
├── metadata.json           ← exported from notebook Cell 21
└── thumbnails/             ← exported from notebook Cell 21
    ├── 000.jpg
    ├── 001.jpg
    └── ...

Other project types look similar. An sklearn project replaces the .npy and thumbnails with .pkl files. A Gemini API project may need nothing beyond app.py and requirements.txt (with the API key stored in Settings → Secrets, never in the repo).

Writing requirements.txt

List every third-party package your app.py imports. One package per line. Do not include standard library modules (os, json, pickle).

Look at your import statements in app.py. Each one that isn't from the standard library needs a line in requirements.txt:

# If app.py has:           →  requirements.txt needs:
import gradio               →  gradio
import pickle               →  (nothing — standard library)
from sklearn...             →  scikit-learn
from transformers...        →  transformers
import torch                →  torch
from PIL import Image       →  Pillow
import numpy                →  numpy

Step 6: Deploy to Hugging Face Spaces

  1. Create a free account at huggingface.co.
  2. Create a new Space. Click your avatar → New Space. Choose Gradio as the SDK. Name it (this becomes your public URL: huggingface.co/spaces/yourname/yourapp).
  3. Upload files. Use the "Files" tab in your Space to upload app.py, requirements.txt, and all your exported data files. You can drag and drop, or push via Git.
  4. Add secrets (if needed). For API keys: go to Settings → Variables and Secrets → New Secret. Name it (e.g., GEMINI_API_KEY). In your code, access it with os.environ["GEMINI_API_KEY"]. Never put API keys in app.py directly because the repository is public.
  5. Wait for the build. HF installs your requirements and runs app.py. Watch the "Logs" tab. A green "Running" badge means success. Red means check the logs for the error.
Common gotcha: file paths. In Colab, your files might be in /content/ or a subdirectory. In your HF Space, everything is in the same directory as app.py. Use relative paths: open("model.pkl"), not open("/content/drive/MyDrive/model.pkl"). If your thumbnails are in a subfolder, use "thumbnails/000.jpg".

Why This Works Without a GPU

The free tier gives you 2 vCPU and 16 GB RAM, no GPU. That's enough.

The expensive operation, embedding 40 images through CLIP's vision transformer, already happened in Cell 13 of your Colab notebook. The app loads the resulting matrix from disk. At runtime, it encodes one query (a text string or an image) through CLIP and computes a dot product against the saved matrix. Encoding one input takes under a second on CPU. The dot product of a (1, 512) vector against a (40, 512) matrix takes microseconds.

The pattern generalizes: if you can save the expensive computation's output to a file, you can serve it on CPU. An sklearn classifier loads a pickled model and calls .predict() on one input. A Gemini API project sends a network request with no local GPU involved. The only projects that need a GPU at runtime are ones that run a large model on every request with no way to pre-compute (real-time image generation, for example). None of your course projects require that.

Pre-Flight Checklist

Before you upload to HF Spaces, verify:

  1. Your app.py runs locally (python app.py opens a Gradio page you can interact with)
  2. All files your code loads exist in the same directory (no absolute paths from Colab)
  3. Your requirements.txt lists every third-party import
  4. No API keys appear anywhere in your code (use os.environ)
  5. If using PyTorch/Transformers: test that inference works on CPU (set device = "cpu" and verify your function still returns correct results)

Troubleshooting

"ModuleNotFoundError: No module named 'X'" — You're importing something not in requirements.txt. Add it. Remember that package names sometimes differ from import names: you import sklearn but install scikit-learn; you from PIL import Image but install Pillow.

"FileNotFoundError" — Your code tries to load a file that isn't in the Space. Either you forgot to upload it, or the path is wrong. All paths should be relative to the directory containing app.py.

"Space is sleeping" — Normal on the free tier. Apps sleep after ~48 hours of inactivity. The first visitor waits ~30 seconds for it to wake. Open your Space a minute before your presentation.

Build takes forever — PyTorch is large (~2 GB). First build takes 5–10 minutes. Subsequent builds use cached layers. If you don't need PyTorch (pure sklearn project), remove torch and transformers from requirements, and your build will finish in under a minute.

App loads but crashes on first query — Check for a hardcoded device = "cuda" from your notebook that fails on HF's CPU environment. The example app.py already handles this with device = "cuda" if torch.cuda.is_available() else "cpu", but if you wrote your own, add that line.

Optional: Skip the Export Step Entirely

The example app.py has a BUILD_COLLECTION flag at the top. When set to True, the app fetches artworks from the Met API, computes CLIP embeddings, and caches everything to persistent storage — all at startup. You don't need to run the Colab notebook or upload any exported files. Your Space's repo contains only app.py and requirements.txt.

This requires two things in your Space's Settings:

  1. Persistent storage. Go to Settings → Persistent Storage and enable it. This mounts a /data/ directory that survives restarts. The app saves its cached collection there so it doesn't re-download and re-embed on every cold start.
  2. A paid hardware tier (optional but recommended). A T4 GPU costs about $0.60/hr and computes 40 embeddings in under 10 seconds. On CPU, the same computation takes 30–60 seconds. Either way it only happens once; after the cache is built, restarts load from disk in under a second.

The first startup builds the cache: the app queries the Met API for public-domain object IDs across several departments, samples 40, downloads each artwork's image and metadata, computes CLIP embeddings, and saves the embedding matrix, metadata JSON, and thumbnails to /data/art_cache/. Every subsequent startup finds the cache and loads it directly. To get a different collection, delete the /data/art_cache/ directory (in the terminal tab of your Space) and restart.

When to use each mode

The default mode (BUILD_COLLECTION = False) is the one this guide teaches. It separates setup code from inference code, which is the skill the deployment exercise is designed to practice. Use it for your portfolio submission.

BUILD_COLLECTION = True is a convenience for after the course, or for projects where you want the app to be fully self-contained. It's also useful if you want to iterate on collection size or department mix without round-tripping through Colab. The tradeoff: your app depends on the Met API being available at startup, and the first cold start is slow.

Cost control. Set a spending cap in your Hugging Face account settings. If you use a GPU tier, set the Space to sleep when idle, and downgrade to CPU (or pause the Space) after your demo. Persistent storage itself costs a few cents per GB per month.
