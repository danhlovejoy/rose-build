Part 1: The System

Run these cells in order. Read the code as you go. By the end of Part 1, you’ll have a working image retrieval system backed by ChromaDB.

Do not modify Part 1 unless something breaks. The experiments in Part 2 depend on the variable names and data structures created here.

# Cell 1: Setup and dependencies

What it does: Installs all libraries for the image pipeline and imports everything. Prints version numbers for key dependencies.

Installs: chromadb, sentence-transformers, google-genai, tensorflow, scikit-image, einops.

Note: The installs take 30–60 seconds. If chromadb throws a dependency conflict warning, it is safe to ignore. Wait for the “All imports succeeded” message before moving on.

# Cell 2: Configure the Gemini API

What it does: Loads your Gemini API key from Colab Secrets and creates a Gemini client. Sends a test prompt to confirm the connection.

Note: If you get an authentication error, check that the secret is named exactly GEMINI_API_KEY and that notebook access is toggled on.

# Cells 3–3b: Load and preprocess images

What it does: Loads your image dataset, resizes all images to 224×224 for MobileNetV2, and applies the model’s preprocessing function. Also generates an index sheet (image_index_sheet.jpg) you’ll reference in Experiment 1.

Dataset choice: Set DATASET at the top of the cell. Two options:

  • flowers — Oxford/TF Flowers. Five species (daisy, dandelion, roses, sunflowers, tulips). Natural photos at 300–500px. Fine-grained: the classes look similar, so retrieval has to work harder.
  • imagenette — A 10-class subset of ImageNet (tench, English springer, cassette player, chain saw, church, French horn, garbage truck, gas pump, golf ball, parachute). Visually diverse: good for testing whether the model separates distinct objects.

Caching: Images and preprocessed arrays are cached to Google Drive. Subsequent runs load from cache.

# Cell 4: Extract image embeddings

What it does: Loads MobileNetV2 as a feature extractor (no classification head, global average pooling) and produces a 1,280-dimensional embedding per image.

Caching: Image embeddings are cached to Google Drive.

# Cells 5–5b: Build ChromaDB image collection

What it does: Creates an in-memory ChromaDB client with a collection containing all image embeddings and their class labels. Cell 5b lets you peek inside the database — what a single record looks like, how the embedding vector is stored alongside the label.

Traditional databases store rows and match exact keywords. Vector databases store embedding vectors and match by similarity — give me the 5 nearest vectors to this query. Each image is stored as a 1,280-dimensional vector. To find similar images, ChromaDB computes the distance between the query vector and every stored vector, then returns the closest ones.

# Cell 6: Search and visualization functions

What it does: Defines search_images_by_image(query_idx, n) for image retrieval and show_image_retrieval(query_idx, n) for displaying results with labels, similarity scores, and match markers. Also generates an index sheet of all images with their indices for reference.

Part 1 checkpoint. You should now have a working image retrieval system backed by ChromaDB. If anything above threw an error, fix it before continuing — every experiment in Part 2 depends on these variables and functions.

Part 2: Experiments

Four experiments, each asking a different question about how the image vector space works. Run the code, record what you find, and write the markdown reflection for each one. The reflections are the substance of your demo.

Experiment 1: The Similarity Game

The question: Does MobileNetV2’s ranking of “similar” match yours? When you look at an image and predict which others the model will rank as most similar, are you right?

The procedure:

  1. The cell displays your image index sheet — a grid of all images with their indices and class labels.
  2. Pick a query image. Before running retrieval, write down which image you predict will be the model’s #1 match and why.
  3. Run retrieval. Compare the model’s results to your prediction.
  4. Repeat for at least five images from different classes.

Experiment 2: Embedding Surgery

The question: Embedding vectors aren’t just opaque numbers — they have geometric structure. If you average two embeddings, does the midpoint land somewhere meaningful?

The procedure:

  1. Pick two images from different classes. Average their embeddings. Retrieve the closest image to the midpoint.
  2. Try it with three images from three different classes.
  3. Try averaging two images from the same class. Does the midpoint retrieve something “more typical” — a more prototypical example of that class?
  4. Try subtracting: take image A’s embedding, subtract image B’s embedding, and retrieve the nearest image. What does the “difference vector” point to?

Experiment 3: The Caption Bridge

The question: Your ChromaDB collection indexes images by visual similarity — you query with an image and get back similar images. But what if you wanted to search by text? “Show me a red flower” or “find the church.” The image embeddings (1,280d from MobileNetV2) and text embeddings (768d from a sentence transformer) live in completely different vector spaces, so you can’t directly compare them.

The workaround: caption every image with Gemini Vision, embed the captions as text, and build a second ChromaDB collection. Now you can query by text and retrieve the image whose caption is most similar.

The procedure:

  1. Run the setup cell to caption all images and build a text index. (This takes 1–2 minutes; captions are cached to Google Drive.)
  2. Write five text queries describing images you know are in your dataset.
  3. For each query, compare what you expected to find with what the caption-based search returned.
  4. Find a case where the bridge works well and a case where it breaks. What made the difference?

Experiment 4: Retrieval Quality Deep Dive

The question: How good is this retrieval system, measured objectively? Precision@k tells you: for each query image, of the top k results, how many share the query’s class? A perfect system scores 1.0 at every k. Where does yours fall short, and which classes cause the most confusion?

The procedure:

  1. Run the evaluation cell to compute precision@k across all images.
  2. Examine the per-class breakdown. Which classes have the highest precision? Which have the lowest?
  3. Find a specific failure case — a query where the model returned the wrong class in the top result. Display it and explain what visual feature caused the mismatch.
  4. Compare to what you observed in Experiment 1: do the classes you predicted would be hard actually show lower precision?
